# 同步策略与异常处理

## 目的

用于统一客户端、服务端、测试与客服对同步流程和异常处理的理解，减少上线后“数据为什么没同步”的沟通成本。

## 当前同步模型

- 客户端通过 `/api/sync/data` 进行整包拉取和整包上传
- 鉴权方式：Bearer Token
- 同步载荷：`goals / tasks / dayEvents / pomodoros / updatedAt`
- 前台/登录后会触发同步

## 当前已实现能力

- 支持拉取云端数据
- 支持上传本地整包数据
- 支持基于 `updatedSince` 的轻量“是否变化”判断
- 登录后支持本地与云端合并
- 鉴权失败时保留本地数据，不做破坏性覆盖
- 核心接口已补充 `traceId`，便于前后端联调与日志定位
- 核心失败响应已补充 `errorCode`，便于客户端和客服识别错误类型

## 当前错误返回约定

- 成功响应保留 `success: true`，并附带 `traceId`
- 失败响应统一包含 `success: false`、`errorCode`、`message`、`traceId`
- 服务端会通过 `X-Trace-Id` 响应头返回同一个追踪 ID
- 当前已接入的核心路径：
- `index.js` 全局错误处理与鉴权中间件
- `routes/auth.js`
- `routes/sync.js`

## 当前限制

- 暂未实现字段级冲突合并
- 暂未实现多端并发修改仲裁
- 暂未实现精细化重试队列
- 暂未实现用户可见的同步冲突解释页

## 用户侧异常文案建议

- 鉴权失效：请重新登录后再试
- 网络异常：网络不可用，已保留本地数据
- 服务端失败：云端暂时不可用，请稍后重试
- 冲突待定：检测到多端修改，建议先检查最新数据后再继续编辑

## 客服排查建议

- 先确认用户是否已登录正式账号
- 再确认是否发生过多设备同时编辑
- 再核查服务端 `/health`、MongoDB、`/api/sync/data` 日志
- 若为会员/IAP 相关状态差异，额外核查 `/api/iap/*` 日志与订单状态

## 建议监控项

- `/api/auth/*` 4xx / 5xx 比例
- `/api/sync/data` 成功率
- 同步平均耗时
- JWT 鉴权失败次数
- 登录成功率
- 注销接口成功率
- IAP 验单成功率
